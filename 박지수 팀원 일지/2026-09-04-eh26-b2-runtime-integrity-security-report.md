# RAG 실행 경로 보안 강화 보고서

작성일: 2026년 9월 4일
대상 작업: `EH2.6.b2` 실행 설정·런타임 권한 봉인
대상 커밋: `780bbd88d20b445cb6f91a37eb93a8483c85fca9`

## 1. 한눈에 보는 결과

이번 작업에서는 RAG 검색을 시작하기 전에 연결된 구성요소가 승인된 설정과 코드인지 확인하는
**실행 무결성 방어 계층**을 만들었다.

외부 해커가 네트워크로 침입하는 상황을 막은 것은 아니다. 프로그램 내부에서 검색기나 설정이 바뀌거나,
테스트용 구성요소가 실제 실행 경로에 섞이거나, 검증 함수 자체가 교체되는 상황을 실행 전에 찾아내는
방어 작업이다.

핵심 결과는 다음과 같다.

- 내부 실행 경로의 공격·변조 시나리오 10종을 방어했다.
- 문제가 발견되면 검색기, 임베딩 모델, 생성 모델, API, Langfuse를 호출하기 전에 중단한다.
- 집중 테스트 104개와 전체 테스트 1,109개를 모두 통과했다.
- 저장소 안전 검사 811개 파일을 통과했다.
- 독립 검토에서 발견된 P1 문제 10건을 수정하고 재검토를 통과했다.

## 2. 왜 필요한 작업이었나

RAG는 여러 부품이 이어져 동작한다.

```text
질문
  → 실행 설정
  → EvidenceStore
  → KURE Dense 검색
  → Kiwi BM25 검색
  → RRF 결과 결합
  → 검증·재랭킹
  → 답변 생성
```

이 가운데 하나라도 실행 중에 다른 구현으로 바뀌거나 잘못된 인덱스와 연결되면 결과를 믿기 어렵다.
테스트용 가짜 검색기가 실제 환경에 들어가거나, 설정 파일의 해시만 맞춘 채 내부 값이 바뀌는 경우도
문제가 된다. 더 위험한 경우는 안전 검사를 담당하는 함수 자체가 교체되는 상황이다.

이번 보강은 이런 문제를 실제 검색이나 모델 호출보다 먼저 차단하도록 만들었다. 문이 열린 뒤 침입자를
찾는 방식이 아니라, 문을 열기 전에 열쇠와 잠금장치, 연결된 부품을 함께 확인하는 방식이다.

## 3. 방어한 공격·변조 시나리오 10종

아래 항목은 외부 CVE나 침투 공격 10건을 뜻하지 않는다. 독립 코드 검토와 적대적 테스트에서 다룬
**Python 런타임 내부 변조 유형 10종**을 발표용으로 묶은 것이다.

| 번호 | 공격·변조 유형 | 쉽게 말하면 | 막은 방법 이름 |
| ---: | --- | --- | --- |
| 1 | 검증 함수 교체 | 안전 검사를 담당하는 함수를 가짜 함수로 바꾼다. | **Root Gate 고정** |
| 2 | 검사 별칭 동시 교체 | 같은 검사 함수를 가리키는 이름을 여러 개 함께 바꿔 검사를 우회한다. | **Call-site Anchor 검증** |
| 3 | 복제 namespace 위조 | 정상 모듈처럼 보이는 복사본을 만들고 내부 함수끼리 서로 정상이라고 속인다. | **Exact Identity 봉인** |
| 4 | 함수 내부 코드 변조 | 함수 이름은 그대로 두고 실행 코드, 전역값 또는 기본값만 바꾼다. | **Code·Globals·Defaults 고정** |
| 5 | 클래스 메서드·descriptor 변조 | 클래스의 메서드나 속성 접근 동작을 바꿔 검사 중 악성 코드를 실행한다. | **Class·Descriptor Attestation** |
| 6 | Registry 교체·항목 위조 | 승인된 구성요소 목록 자체를 바꾸거나 가짜 항목을 끼워 넣는다. | **Registry Identity·Entry Type 검증** |
| 7 | Weak reference 선실행 | 약한 참조를 먼저 읽게 만들어 타입 검사 전에 다른 동작이 발생하게 한다. | **Pre-dereference Type Gate** |
| 8 | Store 탐색 중 부작용 | EvidenceStore나 인덱스를 확인하는 과정에서 getter·hash 함수가 먼저 실행된다. | **Zero-dispatch Store Preflight** |
| 9 | 설정·증명값 동시 위조 | 설정값과 검증용 proof를 함께 바꾸고 해시를 다시 계산해 정상처럼 보이게 한다. | **Factory-issued Hash Binding** |
| 10 | 실행 환경·provider 혼합 | 테스트 runtime, 실제 runtime, 미승인 verifier·reranker·provider를 섞어 호출한다. | **Execution-kind Allowlist + Fail-closed** |

## 4. 실제로 막은 방식

### 실행 설정을 한 곳에서만 발급

`HarnessExecutionConfig`는 아무 코드에서나 임의로 만들 수 있는 값이 아니다. 승인된 factory에서 만든
객체만 사용하며, 설정 내용과 해시를 함께 확인한다. 설정값과 proof를 같이 바꿔도 원래 발급 권한까지
복원할 수 없도록 했다.

### 실제 환경과 시험 환경을 분리

production runtime과 synthetic runtime을 다른 실행 종류로 구분했다. 실제 환경에서는 loader가 확인한
KURE, Kiwi, RRF와 내부 시계만 사용할 수 있다. 시험용 객체를 실제 환경에 섞으면 실행 전에 거부한다.

### 겉모습뿐 아니라 내부 연결까지 확인

함수 이름이나 해시 하나만 보는 것으로 끝내지 않았다. 함수 코드, 전역값, 기본값, 클래스 메서드,
descriptor, registry와 registry 항목까지 확인했다. 정상 함수와 같은 이름을 가진 복사본이나 일부만 바꾼
객체도 거부하도록 했다.

### 검사가 끝나기 전에는 아무것도 호출하지 않음

검사 과정에서 검색기나 모델을 먼저 호출하면 차단이 늦어진다. 그래서 EvidenceStore 탐색, 벡터 접근,
Kiwi tokenizer, verifier, reranker, provider, clock보다 검증이 먼저 끝나도록 순서를 고정했다.
이 원칙을 `zero-dispatch`라고 기록했다.

가장 중요한 결과는 오류를 발견했다는 사실만이 아니다. 오류가 있는 상태에서 외부 모델이나 검색기가
먼저 실행되지 않았다는 점이다. 잘못된 구성은 비용과 부작용이 발생하기 전에 멈춘다.

## 6. 이 작업이 지킨 범위

- EvidenceStore와 검색 대상 데이터의 연결
- KURE Dense 검색기와 벡터 인덱스의 연결
- Kiwi BM25 tokenizer와 lexical index의 연결
- Dense·lexical 결과를 합치는 RRF 구성
- production/synthetic runtime 구분
- verifier와 reranker 사용 권한
- 실행 설정, artifact와 내부 registry의 동일성
- API·모델 호출 전 fail-closed 경계

## 7. 정확한 한계

이 작업은 검색 정확도를 직접 높인 작업이 아니다. 다음 항목과는 구분해야 한다.

- Recall, MRR, nDCG 같은 검색 성능을 개선한 결과가 아니다.
- 외부 네트워크 침입, 운영체제 취약점 또는 계정 탈취를 막는 보안 솔루션이 아니다.
- API 키 관리, 방화벽, 접근 권한, 개인정보 마스킹을 대신하지 않는다.
- 실제 검색 실행과 상태 전이, 답변 생성, 골든셋 성능 비교는 후속 작업이다.

따라서 발표에서는 **“RAG 검색 성능을 높였다”**고 설명하면 안 된다. 대신
**“검색 실험 결과를 믿을 수 있도록 실행 구성의 변조와 오연결을 사전에 차단했다”**고 설명하는 것이
정확하다.

## 8. 발표자료용 요약

### 문제

여러 검색기와 모델을 조합하는 과정에서 잘못된 구성요소가 섞이거나 검증 코드가 바뀌면 실험 결과와
비용 기록을 믿기 어렵다.

### 해결

EvidenceStore, KURE, Kiwi BM25, RRF와 runtime 설정을 하나의 승인된 실행 계약으로 묶었다. 함수 코드,
클래스, registry와 내부 연결을 실행 전에 확인하고, 이상이 있으면 외부 호출 없이 중단하도록 했다.

### 결과

내부 변조 시나리오 10종을 차단했다. 집중 테스트 104개, 전체 테스트 1,109개, 저장소 안전 검사 811개를
통과했으며 검증 중 외부 호출은 0회였다.

### 의미

성능 개선 후보를 비교할 때 “코드가 우연히 다른 부품을 사용했다”는 문제를 줄였다. 이후 골든셋 A/B에서
나오는 차이를 아키텍처 변경 효과로 더 안전하게 해석할 수 있다.

## 9. 발표할 때 쓸 수 있는 문장

> RAG 성능 실험 전에 실행 무결성 계층을 구축했습니다. EvidenceStore, Dense, Kiwi BM25, RRF와 runtime
> 설정을 함께 봉인하고 내부 변조 시나리오 10종을 차단했습니다. 잘못된 구성이 발견되면 검색기나 API를
> 호출하기 전에 중단하며, 집중 테스트 104개와 전체 테스트 1,109개를 통과했습니다. 이 작업은 검색 점수를
> 직접 높인 것은 아니지만 이후 아키텍처 A/B 결과를 신뢰할 수 있게 만드는 안전 기반입니다.
