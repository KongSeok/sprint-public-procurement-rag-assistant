## VM에서 진행한 작업

### 1. KURE 임베딩과 HB 검색 색인을 만들었다

기존 L4 VM과 그 안에서 실행 중인 `Qwen/Qwen3-8B-AWQ` 서버를 사용했다. 새 모델을 내려받거나 다른 팀원의 서버 설정을 바꾸지는 않았다. 03:38에는 KURE가 GPU에서 임베딩을 만들고 Qwen8B가 JSON 답변을 반환하는지 간단히 확인했다. 이 연결 점검은 전체 성능 평가와 별개다.

HB의 Parent-Child 방식을 참고했다. 작은 청크를 검색한 뒤 답변을 만들 때는 더 넓은 부모 문맥을 전달했다. 의미 검색과 BM25를 같은 비중으로 합쳤다. HB 원본을 그대로 재현한 실험은 아니므로, 결과는 이번에 고정한 구성의 결과로 본다.

| 항목 | 이번 실행에서 사용한 구성 |
| --- | --- |
| 문서 | 동결한 refined 자료 98개 |
| 검색용 작은 청크 | 14,012개 |
| 답변에 전달할 부모 문맥 | 3,346개 |
| 임베딩 | KURE, CUDA |

06:04:28에 임베딩과 검색 색인 저장을 끝냈다. 임베딩 자체는 479.458초, 색인 생성 작업 전체는 628.853초가 걸렸다. 입력은 3,870,160토큰이었고 중간 저장 기록 15개와 결과 해시를 확인했다.

06:21:54에는 다른 프로세스에서 같은 색인을 다시 불러오는 데 성공했다. 재임베딩은 하지 않았다. 이후 생성 오류를 고칠 때도 이 색인과 검색 결과를 유지했다. 이 작업으로 `HB8B.1`의 색인 준비를 마쳤다.

### 2. 전체 131개를 실행하고 오류를 분류했다

일반 질문, 조건에 맞는 문서 목록을 찾는 질문, 전체 자료를 집계하는 질문을 같은 생성 경로에 연결했다. 초기 연결 시험에서는 원문 위치 정보가 프롬프트에 중복으로 들어가 일반 질문 하나가 입력 한도를 넘었다. 상세 위치 정보는 별도 근거 기록에 남기고 중복 입력을 정리했다. 그 결과 해당 입력이 26,403토큰에서 6,270토큰으로 줄었고, 검색 결과 4개와 출처 정보 81개는 보존했다.

수정 후 세 유형의 연결 시험을 통과하고 나머지 문항까지 실행했다. 08:43에는 전체 기록을 바탕으로 검색 지표와 기록 형식을 채점했다.

| 전체 131개의 구성 | 결과 | 해석 |
| --- | ---: | --- |
| RAG 질문 | 129개 | 답변 41개, 기권 2개, 오류 86개, 대기 0개 |
| 파서 회귀 | 2개 | 2개 통과. 생성 답변의 정답률과 별도 |
| 출력 상태와 필드 조건이 맞지 않은 오류 | 52개 | 답변과 기권에 필요한 필드 조건이 생성 지시와 후처리에서 달랐다 |
| 입력 문맥 초과 | 26개 | 부모 문맥 등을 포함한 입력이 7,168토큰을 넘었다 |
| 기타 출력 오류 | 8개 | 인용 상한 3개, 출력 잘림 2개, 목록 응답의 ID 오류 3개 |

답변과 기권을 합친 정상 종료 43개를 정답 43개로 세면 안 된다. **이 시점에는 답변 내용의 정답성을 Sol로 채점하지 않았다.** 전체 실행 기록은 확보했지만, 정상 운영에 쓸 기준선으로 확정하지는 않았다.

검색의 문서 Recall@5는 98.40%였다. 일반 질문 106개 중 정답 근거 문서가 있는 94개를 평가한 수치이며, 평가할 수 없는 12개는 따로 남겼다. 이 검색 점수를 전체 131개의 답변 정답률로 해석하지 않는다.

전체 재개 실행은 1,249.004초가 걸렸다. 조기 실패를 포함한 RAG 129개의 기록상 지연은 중앙값 7.039초, 95백분위 42.491초였다. 정상 답변만의 응답시간은 아니다. 이번 실행에서 외부 API는 호출하지 않았지만, 이것이 VM 사용 비용도 없다는 뜻은 아니다.

이 결과를 `HB8B.3`의 첫 전체 실행과 `HB8B.4.a`의 결정론 채점 기록에 남겼다. 이전 검색 실험은 평가 분모와 지표가 달라 이번 결과와 숫자만 나란히 놓고 우열을 정하지 않는다.

### 3. 출력 형식을 고치고 같은 4개를 다시 실행했다

처음에는 답변할 때와 기권할 때 필요한 JSON 필드 조건을 고쳤다. 로컬 검사에서는 통과했지만, 11:02부터 VM에서 같은 4개를 실행하자 모두 다시 실패했다. 3개는 대부분 공백을 출력하다가 토큰 한도에 걸렸고, 1개는 필수 필드가 빠졌다. 서버에서 응답을 받았다는 사실만으로 정상 처리됐다고 볼 수 없었다.

설치된 구조화 출력 처리 방식에 맞춰 답변과 기권의 필드 조건을 다시 정리하고, 프롬프트의 중복 지시도 줄였다. 13:15에 같은 4개를 다시 실행했다.

| 같은 4개에 대한 VM 생성 시험 | 11:02 시험 | 13:15 수리 후 시험 |
| --- | ---: | ---: |
| 정상 출력 | 0개 | 답변 3개, 기권 1개 |
| 오류 | 4개 | 0개 |
| 출력 형식과 엄격 검증 통과 | 0/4 | 4/4 |
| 생성 호출 시간 합계 | 80.44초 | 17.819초 |
| 입력 / 출력 토큰 | 20,614 / 3,087 | 20,286 / 475 |

수리 후 4개는 모두 정상 종료했고 재시도는 없었다. 별도 검수에서도 실제 요청, 응답, 형식 검사 결과가 기록과 일치함을 확인했다. 공유 VM의 부하와 호출 시점이 다르므로 두 시간을 통제된 속도 비교로 쓰지는 않는다.

이 4개는 처음 상태 오류가 난 52개 중 일부다. 저장된 오류 52개를 검사한 결과와 새로 생성한 4개를 더해 56개가 복구됐다고 세지 않는다. 나머지 48개는 아직 다시 생성하지 않았다. 또한 4/4는 출력 형식 통과이지 정답률 100%가 아니다.

이번 시험은 기존 검색 결과를 고정하고 생성만 다시 돌렸다. 재임베딩, 검색 재실행, 전체 131개 재평가는 하지 않았다. `HB8B.5.1a`의 완료 범위는 이 4개의 출력 계약 수리 확인까지다.
