# Evidence-Harness 2단계 구현 진행 보고서

작성일: 2026년 9월 4일
대상 구간: `EH2.1`부터 `EH2.6.b2`까지
작업 브랜치: `feat/total-integration`

## 1. 이번 작업의 목적

현재 서비스 기준선은 Mini131 로컬 베이스라인이다. Evidence-Harness는 이 기준선을 바로 대체하는 완성품이
아니라, 더 정확하고 효율적인 RAG 구조를 찾기 위해 구현 중인 비교 실험군이다.

이번 작업의 목표는 검색 점수를 먼저 높이는 것이 아니었다. 질문을 계획하고, 필요한 근거를 빠짐없이
추적하고, 실행에 사용한 검색기와 상태를 검증할 수 있는 기반을 만드는 일이었다. 이 기반이 완성되면 같은
골든셋과 같은 생성 조건에서 Mini131 기준선과 Evidence-Harness를 비교하고, 실제 결과가 더 나을 때만
승격한다.

## 2. 이전, 현재, 목표

| 구분 | 사용 상태 | 검색·답변 구조 | 검증 상태 |
| --- | --- | --- | --- |
| 이전 기준선 | 현재 실행 가능한 기준선 | Mini131 로컬 검색과 생성 | 기존 골든셋 기준값 보유 |
| 현재 Evidence-Harness | 구현 중인 실험군 | 계획, 인용 후속검색, 비교 범위, 상태·행동, 실행 권한 기반까지 구현 | 코드 회귀 검증 완료, RAG 성능 비교 전 |
| 목표 구조 | 후속 구현 후 후보 | bounded controller가 검색·검증·종료를 실행하고 생성·UI까지 연결 | 동일 골든셋 A/B 후 채택 여부 결정 |

따라서 현재 사용자가 직접 쓰는 기본 경로는 Mini131이다. Evidence-Harness는 핵심 부품이 많이 구현됐지만
전체 실행 제어기와 최종 답변 연결이 남아 있어 아직 기본 번들이 아니다.

## 4. 단계별 핵심 결과

### EH2.1·EH2.2: 질문을 실행 계획으로 바꾸는 규칙

질문 유형, 사용할 예산, 문서 범위와 필요한 작업을 구조화된 `QueryPlan`으로 만든다. 같은 질문은 같은
계획이 나오도록 규칙과 카탈로그 버전을 고정했다. 문서명이 모호하거나 범위가 비어 있으면 임의로 대상을
선택하지 않고 미해결 사유를 남긴다.

### EH2.3: 실제 인용에 근거한 후속검색

사용자가 "그 사업은?"처럼 이어 묻는 경우 이전 답변 문장을 그대로 믿지 않는다. 실제로 인용된 문서와
근거가 같은 저장소에 있는지 다시 확인한 뒤 검색 범위를 이어받는다. 확인된 근거가 부족할 때만 제한된
전역 검색을 한 번 허용하며, 기본 검색과 예외 검색을 기록상 구분한다.

### EH2.4: 여러 문서를 빠짐없이 비교하는 확인표

비교할 문서와 항목의 모든 조합을 만들고 각 칸을 해당 문서 안에서 따로 검색한다. 관련 청크를 찾은 것과
실제 값을 검증한 것을 구분하며, 일부 문서나 항목이 비어 있으면 완전한 비교로 끝내지 않는다.

- [EH2.4 상세 보고서](./2026-09-04-eh24-compare-doc-field-coverage-report.md)

### EH2.5: 근거 상태와 다음 행동을 같은 형식으로 관리

후속검색과 비교검색의 결과를 `Belief`, `Progress`, `HarnessState`로 통합했다. 어떤 근거가 후보인지,
검증됐는지, 아직 찾지 못했는지, 서로 충돌하는지를 분리한다. 현재 상태에서 허용되는 다음 행동과 그
순서도 결정론적으로 계산하고, 결정 기록이 중간에 바뀌지 않았는지 재검증한다.

이 단계는 실행 반복문이 아니다. 상태와 행동 계약을 만든 단계이며 실제 검색 실행과 상태 전이는 EH2.6이
담당한다.

### EH2.6.a: 실행 제어기의 책임 경계 확정

사실 확인, 비교, 후속질문이 어떤 검색 경로를 거치고 언제 멈춰야 하는지 계약으로 정했다. 검색 결과가
없다는 이유만으로 바로 정보 부재를 확정하지 않고, 허용된 검색 행동을 모두 수행했는지 확인한 뒤
종료하도록 경계를 세웠다.

### EH2.6.b1: 단일 사실 질문의 실행 권한

질문 계획, 카탈로그, 실행 설정과 EvidenceStore가 같은 실행에서 나온 것인지 확인하는 `BoundFact`를
구현했다. 존재하지 않거나 오래된 문서 ID는 답변 가능한 상태로 올리지 않는다. 아직 실제 필터링 증명이
없는 메타데이터 조건도 실행 완료로 취급하지 않는다.

### EH2.6.b2: 검색기와 설정이 바뀌지 않았는지 실행 전에 확인

EvidenceStore, KURE Dense, Kiwi BM25, RRF와 실행 설정을 하나의 승인된 실행 계약으로 묶었다. 시험용
검색기나 바뀐 함수가 실제 경로에 섞이면 모델이나 검색기를 호출하기 전에 중단한다. 이 단계의 자세한
방어 범위와 검증 수치는 별도 보고서에 정리했다.

- [EH2.6.b2 상세 보고서](./2026-09-04-eh26-b2-runtime-integrity-security-report.md)

## 5. 전체 변경량

작업 시작 직전 커밋부터 EH2.6.b2 완료 커밋까지의 최종 차이를 기준으로 집계했다.

| 구분 | 파일 수 | 추가 | 삭제 |
| --- | ---: | ---: | ---: |
| 실행 코드 | 17개 | 17,056줄 | 93줄 |
| 테스트 | 14개 | 7,923줄 | 4줄 |
| 계약·기록 문서 | 18개 | 809줄 | 38줄 |
| 합계 | 49개 | 25,788줄 | 135줄 |

총 11개 커밋이 만들어졌다. 마지막 기록 기준으로 집중 테스트 104개, 전체 회귀 테스트 1,109개, 저장소
안전 검사 811개 파일이 통과했다. 이 숫자는 구현 안정성 검증 결과이지 Recall, nDCG, 답변 정확도 같은
RAG 성능 점수가 아니다. 이 구간의 검증에서는 API, 생성 모델과 Langfuse를 실제로 호출하지 않았다.

## 6. 현재 남은 작업

Evidence-Harness 2단계 전체는 아직 완료되지 않았다. 바로 이어질 작업은 다음과 같다.

1. `EH2.6.b3`에서 검색 의무와 Dense·Kiwi 검색 결과 영수증을 분리한다.
2. 실제 행동 효과와 상태 전이를 연결하고 반복 횟수, 시간 제한, 진전 없음 조건을 적용한다.
3. 모든 허용 검색을 마친 뒤에만 정보 부재를 확정한다.
4. 최종 상태를 답변 생성과 Streamlit 화면에 연결한다.
5. Mini131 기준선과 Evidence-Harness를 같은 골든셋, 생성 모델, 평가 조건으로 비교한다.

골든셋 비교 전에는 Evidence-Harness가 더 정확하거나 효율적이라고 결론 내리지 않는다. 구현 테스트와
검색·답변 성능평가는 별개의 검증이다.

## 7. 발표용 요약

> 현재 서비스 기준선은 Mini131 로컬 베이스라인이며, Evidence-Harness는 더 나은 RAG 구조를 찾기 위한
> 실험군입니다. 이번 작업에서는 질문 계획, 실제 인용 기반 후속검색, 문서별 비교 범위, 근거 상태와 행동,
> 실행 설정과 검색기 검증 기반을 구현했습니다. 49개 파일에서 코드와 테스트, 계약 문서를 보강했고 마지막
> 기준 전체 테스트 1,109개를 통과했습니다. 아직 전체 controller와 답변 생성 연결이 남아 있으므로 성능
> 개선을 주장하지 않으며, 구현을 마친 뒤 같은 골든셋으로 기준선과 비교해 채택 여부를 결정합니다.
