# Philosopher / Coder 협업

두 역할이 증거와 질문을 주고받으며 승인된 목표까지 진행한다. 코더의 보고만으로 완료를
승인하지 않고, 검수자도 실험 증거 없이 설계가 우수하다고 선언하지 않는다.
이 스킬은 **문서형 협업 프로토콜**이다. 모델 전환기, 상주 스케줄러, 권한 격리기,
기계적 승인 검증기를 설치하지 않는다. 실제 도구 권한은 실행 환경이 결정한다.

## 역할과 경계

| 역할·모드 | 담당 | 허용 업무 | 제한 |
| --- | --- | --- | --- |
| Philosopher / Design | `gpt-6-astra` | 목표·가설·계약·TODO 설계, 기술 조사, 질문 응답, 재계획 | 제품 코드·테스트 구현 금지, 사용자 요구·예산·데이터 정책 임의 변경 금지 |
| Philosopher / Critic | fresh `gpt-6-astra` | 실제 변경·테스트·방향 검수, 구조화된 판정 반환 | 검수 대상 코드·계약·TODO·증거 파일 수정 금지, 자기 설계를 근거 없이 옹호하지 않음 |
| Coder | `gpt-5.6-sol`, `ultra` | 승인 범위 구현·테스트·실험 실행·수정, 상황·위험·질문 전달, 허용된 통합 실행 | 평가 기준·계약·범위 임의 변경, 자기 승인, 검수 생략, 무단 push 금지 |

검색·실험 전담 역할을 상시 추가하지 않는다. Philosopher는 비교 조건과 해석을 맡고,
Coder는 실행과 원시 증거를 맡는다. 독립 조사·실험 병렬화가 실제로 필요하면 별도로 범위를 정한다.

## 호출 방식: 역할 라우팅, 자기 모델 전환 아님

- 메인 에이전트는 진행·기록을 조정한다. 별도 세 번째 전문 역할이나 LLM을 만들 필요는 없다.
- 메인 모델이 명시적으로 Astra임이 확인되면 Design을 직접 수행해도 된다.
  확인되지 않거나 다르면 지정 모델의 Design 에이전트에 위임한다. 모델 정체성을 추측하지 않는다.
- Coder는 지정 모델로 스폰하고, 수정 지시는 같은 Coder에게 후속 메시지로 보낸다.
  Critic은 매 검수마다 새 에이전트로 스폰한다. 같은 Astra 메인의 자기 검수로 대체하지 않는다.
- 현재 환경에 `collaboration.spawn_agent`가 있으면 Coder에
  `model: "gpt-5.6-sol", reasoning_effort: "ultra", fork_turns: "none"`을 명시한다.
  Critic에는 `model: "gpt-6-astra", fork_turns: "none"`과 검수 패킷을 전달한다.
  Philosopher의 강도는 사용자 설정 또는 호출 환경의 지원 기본값을 유지하고 기록한다.
- 같은 모델·강도를 보장하는 다른 위임 도구도 가능하지만, 지원 파라미터를 먼저 확인한다.
  `ultra`는 여기서 Codex 실행 설정이다. 이를 원시 API의 유효한 effort 값이라고 가정하지 않는다.
- 자연어 역할 지시나 설정 파일 편집만으로 현재 턴의 모델이 바뀌었다고 말하지 않는다.
  기존 에이전트의 모델 변경 기능이 없으면 새로 스폰한다. 모델·위임 기능이 없으면
  그 배치를 `BLOCKED`로 기록하고 대체 승인을 요청한다. 다른 모델로 조용히 대체하지 않는다.
- `fork_turns: "none"`은 대화 이력 비상속이지 시스템·권한·필수 스킬의 제거가 아니다.
  서브에이전트는 중첩 위임하지 않는다. 독립 작업을 동시에 맡길 때는 파일 소유권을 분리한다.

## 시작 시 원천과 범위 고정

1. 실제 프로젝트 루트·브랜치·기존 수정 사항과 이번 작업 소유 범위를 확인한다.
2. 운영 루트를 먼저 확인한다. 프로젝트의 `fivecircles/agent/`가 있으면 그 `fivecircles/`를,
   독립 fivecircles 저장소처럼 루트에 `agent/`, `requirements/`, `architecture/`가 있으면
   저장소 루트 자체를 사용한다. 둘 다 있으면 프로젝트 README/권위 문서로 확정한다.
   아래 `fivecircles/...` 예시는 확인한 운영 루트 기준으로 해석하며 중첩 폴더를 만들지 않는다.
   운영 루트의 `agent/authority.md`, 기존 `requirements/`, `architecture/todolist.md`를 쓴다.
   기술 명세는 해당 프로젝트가 지정한 기존 `architecture/spec/` 또는 `architecture/specs/`를
   따른다. 새 명세 폴더, `PROJECT_CONTRACT.md`, `TASKS.json`으로 원천을 복제하지 않는다.
3. 최신 사용자 지시와 결정 이유가 기존 문서에 반영됐는지 확인한 뒤 fresh 역할에 전달한다.
   충돌은 기존 권위 순서로 해결한다. 리뷰 결과가 요구사항을 자동으로 뒤집을 수 없다.
4. [메시지 계약](references/messages.md)을 읽는다. 현재 배치의 목표·in/out·수정 파일·완료 조건·
   테스트·실험 통제 조건·중단 조건을 담은 DIRECTIVE를 만든다.
5. 기존 실행 폼에 협업 상태를 붙인다. 필요한 경우에만
   `fivecircles/work/collaboration/<run_id>/`에 `state.json`과 배치별 메시지를 저장한다.
   상태는 작업 ID와 문서 버전/식별자를 참조하며 별도 요구사항·TODO 원장이 되지 않는다.
   원문·키·개인정보·비공개 평가 데이터는 패킷이나 공개 로그에 복제하지 않는다.

## 양방향 실행 루프

릴레이샷/원샷딜에 연결할 때는 [Relay 라이프사이클](references/relay-cycle.md)을
추가로 읽는다. 시작 방향 결정은 Design의 DIRECTIVE이고, 구현 후 PASS는 별도 fresh
Critic의 판정이다. 메인 한 명이 closeout·로그올·허용된 통합 뒤 같은 루프의 시작으로
돌아간다. 관련 스킬의 협업 모드 순서·책임 경계는 해당 레퍼런스를 단일 원천으로 쓴다.

1. **DIRECTIVE → Coder:** 지정 작업을 구현하고 집중 테스트한다. 필요하다면 구현 전
   해석·가정을 회신한다. 승인된 실험 조건을 바꾸지 않고 결과·실패를 모두 남긴다.
2. **QUESTION → Philosopher:** 계약 모순, 없는 입력, 다른 구현 대안, 반복 실패를 만나면
   근거·영향·선택지를 전달한다. 막힌 의존 작업을 멈추고 안전한 독립 작업만 진행한다.
3. **DIRECTIVE 갱신 → Coder:** Philosopher가 답과 이유를 주고 필요하면 범위를 재설계한다.
   Coder는 수락한 지시 버전을 보고에 포함한다. 모순이 남으면 재질문하며 맹목적으로 구현하지 않는다.
4. **IMPLEMENTATION_REPORT → Critic:** 구현·테스트·미완료·편차·질문을 제출한다.
   검수 패킷을 고정한 뒤 해당 후보 파일을 더 수정하지 않는다.
5. **REVIEW → Coder:** fresh Critic이 실제 코드와 증거를 읽고 판정한다. 메인이 응답과
   후보 식별자·검증 조건을 확인해 기록하고 수정 지시 또는 다음 단계로 전달한다.
6. PASS 이후에도 기존 통합 검증·로그올·커밋/push 권한을 확인한다. PATCH는 수정·재검수,
   REPLAN은 허용 범위 재설계, HALT는 사유·재개 조건 기록으로 연결한다.

메시지를 보냈다는 이유만으로 상대가 처리했다고 기록하지 않는다. 명시적 응답·테스트 증거·
도구 완료 결과를 확인한다. 실패·시간초과·잘린 JSON은 `WAITING_REVIEW` 또는 사유 있는
`BLOCKED`이며 PASS가 아니다. 같은 지적의 수정이 두 번 실패하면 REPLAN으로 올린다.

## 검수 시점과 깊이

작은 leaf TODO마다 전체 회귀·보고서를 다시 만들지 않는다. 집중 검증은 leaf마다,
독립 검수와 기존 전체 검증은 합의된 배치/통합 경계에 모은다.

- **필수:** 배치 종료/최종 전달 전 검수. 계약·공개 API·스키마·보안·비공개 전송·평가 기준
  변경은 작업 수와 무관하게 해당 의존 작업을 확대하기 전 검수한다.
- **실패:** 의도된 TDD RED와 예상하지 못한 회귀를 구분한다. 미해결 필수 실패가 있으면
  수리는 가능하지만 다음 의존 배치·통합 승인으로 넘어가지 않는다.
- **보조:** 마지막 PASS 이후 3개 leaf 완료 또는 30분 경과 시 다음 안전한 지점에서
  중간 검수한다. 이 숫자는 초기 운영값이며 변경 가능하다. 테스트·파일 쓰기를 강제로 끊거나
  이 스킬만으로 정시 자동 호출을 보장하지 않는다.
- 위험 점수는 마지막 PASS 이후 관련 변경을 누적해 **깊이 선택**에만 쓴다:
  DB 스키마/공개 API 각 +4, 보안 +3, 수동 코드 변경 500줄 초과 +3,
  의존성 추가/아키텍처 변경/예상 밖 회귀 각 +2, 3개 leaf 완료 +1.
  반복 사건 부풀리기와 생성 파일 LOC는 제외하고 근거를 남긴다.
  0–5는 quick, 6 이상은 deep으로 시작하되 필수 조건은 점수보다 우선한다.
  점수를 낮추려고 배치를 쪼개거나 PATCH 후 위험 이력을 초기화하지 않는다.
  첫 PASS가 아직 없으면 해당 실행/배치 시작 스냅샷을 누적 기준으로 사용한다.
- 보안·평가 무결성·데이터 정책 또는 여러 계층의 계약 변경은 점수와 무관하게 deep 검수한다.
  quick도 관련 전체 diff·필수 증거를 확인한다. deep은 호출자·하위 영향·목표 적합성까지 확장한다.

## Fresh Critic 패킷과 승인 범위

- 대화 전체 대신 DIRECTIVE, 승인된 계약과 이번 변경 제안, 결정 이유, 관련 TODO,
  마지막 PASS 대상, 후보 변경 목록·diff·관련 전체 파일, 테스트 명령·결과·대상 ID를 준다.
  파일 읽기 범위는 의존 관계 확인에 필요한 만큼 확장할 수 있다. 보고자 요약만 믿지 않는다.
- `git diff <last-pass>..HEAD`만으로 충분하다고 가정하지 않는다. staged/unstaged/untracked,
  삭제·이름 변경과 기존 다른 작업자의 수정도 확인해 포함 또는 제외 근거를 적는다.
- 후보는 clean 후보 커밋 또는 파일 목록+콘텐츠 해시의 고정 스냅샷으로 식별한다.
  검수 목적으로 미검증 커밋/push를 강요하지 않는다. 더러운 작업 트리를 정리하려고
  타인의 변경을 stage/reset/stash/delete하지 않는다. 포함 범위를 못 정하면 검수를 보류한다.
- 테스트는 같은 후보와 계약/환경에서 실행된 증거여야 한다. 미커밋 파일에 의존한 성공도
  점검한다. 후보 고정 전 실행한 테스트라면 그 테스트 대상과 후보의 동일성을 확인한다.
- PASS는 해당 후보·계약·테스트 증거만 승인한다. 이후 코드/계약/의존성/평가 설정이 바뀌면
  새 후보로 재검수한다. 후속 필수 검증 실패도 기존 PASS로 덮지 않는다.
- 승인 후 추가되는 closeout 전용 기록은 제품 후보의 입력이 아님을 명시해 별도 기록할 수 있다.
  동작·권위 계약·필수 증거에 영향을 주는 변경을 단순 로그로 분류해 제외하지 않는다.
- last-pass 포인터는 유효한 PASS와 필수 검증을 확인한 뒤에만 갱신한다.
  PATCH/REPLAN/실패한 리뷰를 새 승인 기준선으로 사용하지 않는다.

## 검수 질문

Critic은 다음을 근거로 답한다. 필요 없는 스타일 수정은 blocker로 만들지 않는다.

- 승인된 설계대로 구현됐는가? 그 설계 자체가 현재 목표를 달성하는 데 여전히 적합한가?
- 실제 사용자/검색/생성 경로가 연결되는가, 내부 DTO 테스트만 늘어나는가?
- 변경의 복잡도에 비해 얻는 가치가 충분한가? 더 작은 검증 가능한 방법이 있는가?
- 필수 테스트·실험의 누락과 실패가 정직하게 드러나는가?
- 기준선·동결 데이터/지표·비용/권한 경계를 보존했는가?
- 다음 배치가 목표에 가장 가까워지는 작업인가? 회귀 PASS와 실제 품질 개선을 구분했는가?

## 권한과 기존 스킬 연결

Critic의 수정 금지는 기본적으로 행동 규칙이다. 현재 스폰 도구가 개별 read-only 설정을
제공하지 않으면 **강제 격리됐다고 보고하지 않는다**. 실제 격리를 요구받으면 지원되는
read-only 샌드박스/스냅샷 실행과 쓰기·외부 도구 제한을 확인한 후에만 격리를 주장한다.
권한을 늘리거나 별도 CLI/API 인증·자동화를 이 스킬이 임의로 구성하지 않는다.

- `doc-contract-writer`: Philosopher / Design의 계약 작성.
- `one-go`, `batch-sequential-runner`: Coder의 승인 범위 구현·집중 테스트.
- `peer-review`: Critic의 검수 기준. 이 모드에서 파일 기록 의무는 메인이 수행하고
  Critic은 구조화된 결과만 반환한다. 결과를 받기 전에 APPROVE를 기록하지 않는다.
- `test-runner`: Coder의 실행 증거와 필요한 독립 재검증. 모델 검수로 테스트를 대체하지 않는다.
- `logall`, `relay-shot`: 메인이 판정·증거·다음 지시를 반영한다. 커밋/push 등 외부 변경은
  원래 사용자 권한 안에서만 실행한다. 협업 스킬 활성화 자체는 push나 RAG 실행 승인이 아니다.

기존 배치 스킬의 “총괄자가 직접 코드를 고친다”는 선택지 대신 이 모드에서는 Coder에게
PATCH를 보낸다. 두 에이전트가 같은 파일에 동시에 쓰거나 Critic이 제품 코드 소유자가 되지 않는다.
역할 실패·질문 대기 중에는 후속 의존 배치를 시작하지 않는다. 재개 시 저장된 패킷과 실제
작업 트리를 재확인하고, 통신 이력이 없는 완료를 추정하지 않는다.
